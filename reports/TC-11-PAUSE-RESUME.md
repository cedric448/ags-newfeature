# TC-11 带内存快照与 Pause/Resume 延迟测试

| 项 | 值 |
|---|---|
| 测试例编号 | TC-11 |
| 测试目标 | 测「带内存状态保存/恢复」的最快唤醒路径：Pause/Resume vs 带内存快照 |
| 地域 | `ap-beijing` |
| 网络模式 | `SANDBOX` |
| 规格 | 2C / 4Gi |
| 镜像 | `euson-tcr.tencentcloudcr.com/cedricbwang/test:v1` |
| ProbePeriodMs | 500 |
| 测试日期 | 2026-11-06 |
| 参考 | [auto-snapshot.md](../docs/guides/auto-snapshot.md)（上海 2026-08-12 报告） |
| 结论 | ✅ **Pause/Resume 带内存恢复仅 1.7–2.1s**；❌ **快照不支持 Memory=true** |

---

## 1. 关键发现：快照不支持内存态

直接调用带内存快照被明确拒绝：

```
UnsupportedOperation.SandboxSnapshot
Memory=true is not supported for Runtime Snapshots
```

> **结论：`CreateSandboxSnapshot` 只能做磁盘快照（`Memory: false`）。**
> 想要保留进程/内存状态，**唯一可用的是 Pause/Resume**。
> 这一点与参考文档一致——其 Snapshot 章节也写明「Snapshot 不保存内存态，因此没有 mem / non-mem 维度」。

---

## 2. Pause / Resume 延迟

### 2.1 对照组设计

| 参数 | 值 |
|---|---|
| `PauseSandboxInstance.Memory` | `true`（带内存）/ `false`（仅磁盘） |
| 计时口径 | pause：调 API → 状态变 `PAUSED`；resume：调 API → 状态回 `RUNNING` |
| 轮次 | 每种模式 3 轮 |
| 实例 | 每轮新建，避免复用影响 |

### 2.2 结果

| 模式 | pause r1 | r2 | r3 | **pause 中位数** | resume r1 | r2 | r3 | **resume 中位数** |
|---|---|---|---|---|---|---|---|---|
| **带内存** `Memory=true` | 8.39 s | 8.30 s | 8.50 s | **8.42 s** | 1.52 s | 1.85 s | 2.09 s | **1.85 s** |
| **不带内存** `Memory=false` | 0.43 s | 0.46 s | 0.40 s | **0.43 s** | 1.80 s | 2.15 s | 1.96 s | **1.96 s** |

### 2.3 特征

- **带内存暂停慢 20 倍**（8.42s vs 0.43s）——需要把整个内存 dump 到存储；
- **恢复时间两者接近**（1.85s vs 1.96s），本环境没有体现出带内存恢复的明显优势；
- 与参考文档结论**方向一致**：带内存暂停慢、恢复快；不带内存暂停快、恢复慢。

## 3. 带内存 Resume 是否真的保留内存态？

### 3.1 验证方法

暂停前在实例内留下三类状态：

1. 磁盘文件 `/tmp/m.txt`
2. 后台进程 `sh -c '...; sleep 200000'`（PID 11）及其子进程 `sleep 200000`（PID 13）
3. `/proc/uptime`（系统运行时长）

### 3.2 结果

```
=== PAUSE 前 ===
mem-1794043493
11 sh -c echo mem-1794043493 > /tmp/p.txt; sleep 200000
13 sleep 200000
5.02 11.91                    ← uptime 5.02 秒

pause=8.418s  resume=1.721s

=== RESUME 后 ===
mem-1794043493
---
11 sh -c echo mem-1794043493 > /tmp/p.txt; sleep 200000
13 sleep 200000
---
8.17 20.74                    ← uptime 8.17 秒（接续而非归零）
```

### 3.3 结论

| 检查项 | 结果 |
|---|---|
| 磁盘文件保留 | ✅ |
| **后台进程 PID 不变（11/13）** | ✅ **进程未被重启，内存态真正保留** |
| uptime 接续（5.02 → 8.17） | ✅ 未重置，说明不是重新启动容器 |

**带内存 Pause/Resume 确实保留了进程运行状态**，恢复后不需要重新初始化。

## 4. 磁盘快照（Memory=false）补充数据

| 指标 | 结果 |
|---|---|
| 快照创建耗时 | **0.33 s** |
| `MemoryIncluded` | `false` |
| 恢复耗时（5 轮） | 2.04 / 1.97 / 1.73 / 2.08 / 1.90 s，**中位数 1.97 s** |
| 磁盘文件是否保留 | ✅ `/tmp/disk-marker.txt` 内容完整 |
| 后台进程是否保留 | ❌ 不保留（PID 变了，进程需重新拉起） |

与 TC-10 结论一致：磁盘快照恢复（1.97s）与冷启动（1.87–1.95s）基本持平。

---

## 5. 三条路径横向对比（本环境实测）

| 路径 | 恢复/启动延迟 | 保留内存态 | 保留磁盘 | 适用场景 |
|---|---|---|---|---|
| **冷启动** | 1.87–1.95 s | ❌ | ❌ | 全新实例 |
| **磁盘快照恢复** | 1.97 s | ❌ | ✅ | 同一磁盘状态派生多实例 |
| **Pause/Resume（不带内存）** | 1.96 s | ❌ | ✅ | 临时释放算力、保留磁盘 |
| **Pause/Resume（带内存）** | 1.85 s | ✅ | ✅ | **保留运行中进程/上下文** |
| 带内存快照 | — | — | — | ❌ **不支持** |

> 注：本环境冷启动已足够快（~1.9s），三条路径延迟差异都在 0.2s 内，**单看速度没有赢家**。
> 真正的选择依据是**语义**：是否需要保留内存态、是否需要派生多个实例。

## 6. 与参考文档对比

| 指标 | 参考文档（上海 1C1G） | 本次（北京 2C4G） |
|---|---|---|
| 带内存暂停 | 3.3–3.4 s | 8.42 s（更慢） |
| 带内存恢复 | **568–579 ms** | 1.85 s（更慢） |
| 不带内存暂停 | 487–641 ms | 0.43 s ✅ 接近 |
| 不带内存恢复 | 6.3–6.7 s | 1.96 s（更快） |
| Snapshot 创建 | 0.2–0.3 s | 0.33 s ✅ 一致 |
| Snapshot 恢复 | 6.2–6.4 s | 1.97 s（更快） |

**带内存恢复本次 1.85s，明显慢于参考文档的 568ms**，可能原因：

1. 内存规格不同（4Gi vs 1Gi），dump/restore 数据量更大；
2. 两地域底层存储/宿主机性能差异；
3. 版本演进（参考文档为 2026-08，本次 2026-11）导致实现变化。

## 7. 结论与建议

| 项 | 结论 |
|---|---|
| 带内存快照 | ❌ **不支持**，`Memory=true` 被明确拒绝 |
| Pause/Resume 带内存 | ✅ 可用，暂停 8.42s / 恢复 **1.85s**，进程状态真实保留 |
| Pause/Resume 不带内存 | ✅ 可用，暂停 0.43s / 恢复 1.96s |
| 最快的「保留内存」唤醒 | Pause/Resume 带内存，约 1.85s |
| 暂停配额 | 单账号单地域默认 **20 个**暂停实例 |

**选型建议：**

| 需求 | 方案 |
|---|---|
| 保留运行中进程、上下文、内存 | **Pause/Resume（Memory=true）** |
| 只要保留磁盘数据 | 磁盘快照 或 Pause(Memory=false) 均可 |
| 从同一状态派生多个实例 | 磁盘快照（1 快照 → N 并发恢复） |
| 全新无状态实例 | 冷启动，最快且最省 |

**成本提醒**：带内存暂停耗时 8.4s，若高频切换，累计开销不可忽略；
且暂停实例占用配额（默认 20 个），需注意容量规划。

## 9. 局限

| 项 | 说明 |
|---|---|
| 内存规格单一 | 仅测 4Gi；1Gi/8Gi 下的暂停恢复耗时不同 |
| 未测大内存工作集 | 若进程实际占用几个 GiB，dump 时间会更长 |
| 未测长时间暂停 | 暂停后长时间保持（配额/超时策略）未验证 |
| 未测并发暂停恢复 | 参考文档有 10 并发 Barrier 数据，本次为串行 |
