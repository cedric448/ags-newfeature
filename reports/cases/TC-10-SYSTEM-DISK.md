## 1. 为什么必须进沙箱验证

`Resources.Storage` 声明后，接口会回显一个 `Storage` 值（统一换算为 Mi，如 `50Gi` → `51200Mi`）。

但**回显只能证明参数被接受，不能证明磁盘被真实分配**。若底层只做了配置透传而没有实际扩容，
回显依然会显示声明值。因此本用例的关键设计是：

> 每个场景都进入沙箱执行 `df -B1 /` 与 `findmnt -no SOURCE,FSTYPE,SIZE /`，
> 用**实测字节数**与声明值比对，而不是依赖接口回显。

## 3. 关键发现

### 3.1 实测容量恒小于声明值，且小档位偏差更大

| 档位 | 绝对偏差 | 相对偏差 |
|---|---|---|
| 1Gi | -51 MiB | **-5.0%** |
| 20Gi | -492 MiB | -2.4% |
| 50Gi | -1116 MiB | -2.2% |
| 100Gi | -2181 MiB | -2.1% |
| 150Gi | -1352 MiB | -0.9% |

偏差来自文件系统元数据（inode 表、日志区等），是**固定量级**而非按比例缩放，
因此小容量下的相对偏差更明显。文档中「文件系统开销约 1%，略小于声明值」的描述方向正确，
但 1Gi 档实际偏差达 5%，属于文档描述偏乐观。

> 本用例的判定容差设为 8%，同时输出绝对偏差，避免小档位被误判为失败。

### 3.2 超上限报错信息质量高

```
DiskSize "999Gi" exceeds the system disk limit 150Gi of this account in region ap-beijing;
allowed: 1-100 (1Gi step), 105-300 (5Gi step), or 128/256 up to 150Gi
```

直接给出**本账号实际可用区间**，用户无需查阅文档或提工单即可自行修正。

### 3.3 `Resources` 覆盖是整体替换，不是局部合并

实例级只传 `Storage` 会报 `Resources: CPU is required`。
这是一个实际使用中容易踩的坑：覆盖任何一项资源都必须把 CPU/Memory 一并带上。
