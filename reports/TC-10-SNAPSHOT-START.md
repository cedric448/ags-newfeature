| 项 | 值 |
|---|---|
| 测试例编号 | TC-10 |
| 测试目标 | 验证「从沙箱快照恢复实例」相比「冷启动」是否真的更快 |
| 地域 | `ap-beijing` |
| 网络模式 | `SANDBOX` |
| 规格 | 2C / 4Gi |
| 镜像 | `euson-tcr.tencentcloudcr.com/cedricbwang/test:v1` |
| 测试日期 | 2026-11-06 |

## 1. 关键前提：快照必须用 AgentCBS 系统盘

### 1.1 踩坑：首次创建快照失败

```
UnsupportedOperation.SandboxSnapshot
persistence provider "volume-snapshot" requires a SystemDisk instance
```

与 CBS 数据盘是同一个要求。必须用 `x-ags-agent-cbs-system-disk="true"` 起的实例才能打快照：

```python
ags.call('StartSandboxInstance', {
    'ToolId': tool_id,
    'Timeout': '1h',
    'Metadata': [{'Name': 'x-ags-agent-cbs-system-disk', 'Value': 'true'}],
})
```

### 1.2 快照创建

```python
ags.call('CreateSandboxSnapshot', {
    'InstanceId': instance_id,
    'SnapshotName': 'agstest-snap-xxx',
    'Memory': False,
})
```

实测返回：

```json
{"SnapshotId": "snapshot-01a1b140-de15-8008-a67e-8ce6b18a38fc",
 "Status": "ACTIVE", "MemoryIncluded": false}
```

⚠️ 该接口是 **Runtime Snapshot API，当前为预览版（Beta）**，官方声明「后续可能发生不兼容变更」。

### 1.3 踩坑：从快照启动不能同时传 ToolId

```
InvalidParameter: ToolId, ToolName and TemplateId cannot be provided with SnapshotId
```

必须**只传 `SnapshotId`**：

```python
ags.call('StartSandboxInstance', {'SnapshotId': snapshot_id, 'Timeout': '10m'})
```

## 2. 关键干扰项：健康探测周期

参考文档附录明确指出：创建耗时的 **6.1–6.5s 主要来自健康探测周期**。
本轮实测完全复现了这一点：

| ProbePeriodMs | 冷启动耗时 |
|---|---|
| 2000 | 3.29 s |
| 500 | **2.28 s** |
| 500（另一组） | **1.95 s** |

> 初测时使用默认 `ProbePeriodMs=2000`，得到 4.2–4.8s，其中**绝大部分是探测等待**，
> 掩盖了真实的启动差异。必须先把探测周期压到 500ms 再对比。

---

## 3. 测试结果

### 3.1 串行单实例（中位数）

| 场景 | ProbePeriodMs | 冷启动 | 快照启动 | 差异 |
|---|---|---|---|---|
| 串行 5 轮（首轮含冷加载） | 500 | **1.95 s** | 4.46 s | +128% |
| 串行 3 轮（快照已预热） | 500 | 1.87 s | **1.98 s** | **+6.2%** |
| 串行 3 轮 | 2000 | 3.29 s | 4.64 s | +41% |
| 串行 3 轮 | 500 | 2.28 s | 4.53 s | +99% |

快照启动的逐轮原始值（ProbePeriodMs=500，**同一快照首次使用**）：

| 轮次 | 冷启动 | 快照启动 |
|---|---|---|
| r1 | 1.93 s | 4.31 s |
| r2 | 2.00 s | 4.59 s |
| r3 | 1.94 s | 4.46 s |
| r4 | 1.90 s | 4.42 s |
| r5 | 1.92 s | 4.13 s |

### 3.1b 关键发现：快照首次恢复有冷加载代价

新建快照后连续恢复 **8 次**，耗时稳定而不衰减：

| 轮次 | r1 | r2 | r3 | r4 | r5 | r6 | r7 | r8 |
|---|---|---|---|---|---|---|---|---|
| 耗时 | 1.95 | 1.97 | 1.92 | 1.92 | 2.01 | 1.93 | 1.91 | 1.98 |

**全部落在 1.91–2.01s**，与冷启动（1.87s）基本持平。

> 说明：3.1 表中 4.46s 的异常值来自**另一组快照**——该快照首次恢复时发生了约 2.5s 的
> 一次性加载开销（快照数据首次从存储介质拉取）。一旦预热，后续稳定在 ~1.95s。

### 3.2 并发恢复

| 并发度 | 场景 | 批次墙钟 | 单实例均值 | 成功率 |
|---|---|---|---|---|
| 10 路（快照首次） | 快照恢复 | 5.41 s | 4.68 s | 10/10 |
| 10 路（快照首次） | 冷启动 | **2.57 s** | **1.83 s** | 10/10 |
| 5 路（快照已预热） | 快照恢复 | 2.40 s | — | 5/5 |
| 5 路（快照已预热） | 冷启动 | 2.34 s | — | 5/5 |

预热后两者批次墙钟基本一致（2.40 vs 2.34s）；快照首次恢复那一组明显落后，
同样是首加载代价。**并发本身没有体现出快照优势**——因为本环境下冷启动已经够快，
10 路并发墙钟仅 2.57s，没有可压缩空间。

## 4. 结论

| 检查点 | 结论 |
|---|---|
| 快照能否创建（AgentCBS 系统盘） | ✅ 通过，创建约 0.2–0.3s，秒级 ACTIVE |
| 快照能否恢复实例 | ✅ 通过，串行/并发 25/25 全成功 |
| 快照是否比冷启动快 | ❌ **否，持平（+6.2%）** |
| 并发恢复是否更优 | ❌ 否，预热后 2.40s vs 2.34s，无差异 |
| 首次恢复是否有额外开销 | ⚠️ 有，约 +2.5s 一次性冷加载 |

**判定：在 `ap-beijing`、2C4Gi、SANDBOX 网络模式下，快照恢复实例与冷启动耗时基本持平
（差异 6%，在噪声范围内），没有任何启动加速收益；反而首次恢复会额外付出约 2.5s 的冷加载代价。**

### 4.1 与参考文档的差异

| 指标 | 参考文档（上海 1C1G, 2026-08） | 本次（北京 2C4G, 2026-11） |
|---|---|---|
| 冷启动创建 | 6.1–6.5 s | 1.87–1.95 s |
| Snapshot 创建 | 0.2–0.3 s | ✅ 0.27 s，一致 |
| Snapshot 单实例恢复 | 6.2–6.4 s | 1.98 s（预热后）/ 4.46 s（首次） |
| 相对冷启动 | **持平**（6.4 vs 6.3） | **持平**（1.98 vs 1.87）✅ 结论一致 |

**本次结论与参考文档一致**：Snapshot 恢复与冷启动本就基本持平，**并不更快**。
参考文档的真正收益点在于「**一个快照可并发恢复多个实例**」——10 路并发墙钟从 33s 降到 6.8s，
即**并行度收益**，而非单实例延迟收益。本次环境冷启动本身就只要 2s，10 路并发也只要 2.57s，
没有可压缩的空间，因而看不出差异。

### 4.2 为什么本环境看不到快照收益

1. **冷启动路径已经极快**：排除探测周期后仅 ~1.9s，说明镜像已预热、
   宿主机侧缓存命中，冷启动本身几乎没有可优化空间。
2. **快照恢复没有更快**：预热后 ~2.0s，与冷启动持平——它省掉的是「镜像/容器初始化」，
   但增加的是「快照数据加载与元数据恢复」，两者在当前规格下大致抵消。
3. **首次恢复有一次性开销**：快照数据首次从存储拉取，额外约 +2.5s。
4. **并发无压缩空间**：本环境 10 路冷启动并发墙钟 2.57s，接近单实例耗时，
   已经是并行执行，快照的并行优势无从体现。

### 4.3 与「auto-snapshot 后缀」的关系

TC-09 已证明工具名结尾 `auto-snapshot` **不会触发任何快照机制**。
本 TC-10 走的是**显式快照路径**（CreateSandboxSnapshot + SnapshotId），
这是产品真实提供的快照能力，但从实测看**在当前环境下没有启动加速价值**。

## 5. 复现方式

完整脚本见 `scripts/tc10_snapshot_start.py`：

```bash
# 全流程：建工具 → 起系统盘实例 → 打快照 → 冷启动/快照启动对照
python3 scripts/tc10_snapshot_start.py

# 指定探测周期（关键，默认 500ms）
python3 scripts/tc10_snapshot_start.py --probe-ms 500
```

## 6. 建议

| 场景 | 建议 |
|---|---|
| 单实例快速启动 | **直接用冷启动**，快照无收益且首次还更慢 |
| 大规模批量派生（同一状态起 N 个实例） | 可考虑快照，但需先在目标规格/镜像上复测；参考文档显示其价值在于「1 快照 → N 并发恢复」 |
| 需要保留运行态（进程内存） | 用 `Memory: true` 的**带内存快照**或 Pause/Resume；参考文档显示带内存恢复可到 500–580ms |
| 当前 `auto-snapshot` 后缀 | 无效，不要依赖 |

---

## 7. 局限

| 项 | 说明 |
|---|---|
| 未测带内存快照 | `Memory: true` 恢复可能显著快（参考文档 568ms），本次只测了 `Memory: false` |
| 未测 Pause/Resume | 参考文档显示带内存暂停恢复约 500–580ms，是最快的唤醒路径，未在本环境验证 |
| 样本量 | 每组 3–5 轮，建议生产决策前扩到 ≥30 轮 |
| 镜像偏轻 | 本次镜像冷启动仅 1.9s，重镜像场景结论可能不同 |
| Beta 接口 | `CreateSandboxSnapshot` 为预览版，后续可能变更 |
